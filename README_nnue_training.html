Enyo NNUE Training

This document explains how Enyo NNUE training works: what the network represents, what a training row means, how teacher labels become weight updates, which scripts transform the data, and why replay plus SPRT are required before a network can be called stronger. 

positions -> teacher labels -> packed tensors -> PyTorch training -> .nn export -> replay gates -> SPRT

Glossary links: FEN, JSONL, feature, weight, teacher, label, tensor, PyTorch, packed dataset, .nn export, replay gate, SPRT.

The Core Idea

Enyo search needs an evaluation for leaf positions. The NNUE is a fast function that turns a chess position into one centipawn score. Training adjusts the stored numeric weights inside that function so its score is closer to a stronger teacher's score. 

FEN position
  -> active sparse NNUE features
  -> current network prediction
  -> compare with teacher score
  -> backprop updates weights
  -> exported .nn used by Enyo search

A training row does not say "play this move." It says "in this position, the teacher thinks the side to move is worth this many centipawns." If the network predicts too high or too low, training nudges the weights attached to the active features.

The roadmap, completed checklist, and changing run status belong in NNUE.md. This file explains the training pipeline itself.

Training Data Flow

Training data moves through several representations. Each step has a specific job: choose useful positions, create stronger labels, make the data cheap for PyTorch, train a candidate, then reject anything that does not survive engine validation.

StepWhy it existsScript/toolOutput
Choose positions A huge source pool is too large and usually badly distributed. Sampling chooses a smaller set with the score mix we want. sample_buckets.py source_bucketed.jsonl
Create targets The net needs target scores. A stronger engine is used as the teacher. label_with_uci.py shards/label.*.jsonl
Audit Bad labels waste GPU time and can train a worse net. Audit checks distribution and sanity. audit_targets.py audit_targets.log
Pack Parsing FEN text during every epoch is slow. Packing converts rows into arrays. pack_dataset.py packed/
Train PyTorch changes weights so predictions move closer to teacher labels. train.py model.pt and model.nn

Replay gate Static eval is not enough. Replay checks search behavior in known problem games. replay move changes, blunders, timeouts, regressions

Pipeline Steps In Detail

The short pipeline line is accurate, but each arrow hides an important file format and validation step. The current Enyo pipeline is built around JSONL position rows until packing; after packing, training uses dense NumPy arrays loaded as PyTorch tensors.

1. Positions

Positions are gathered from actual chess games, not from random board generators. The main Enyo-owned source so far is Enyo self-play created by fastchess from opening books, then converted from PGN into one JSON object per useful position.

A position row is stored as JSONL. The key field is fen, a FEN string describing the board, side to move, castling rights, en-passant square, and counters. The row also keeps context from the game so the data can be audited later.

  "move": "a6",
  "move_uci": "a5a6",
  "score": -259,
  "wdl": 1.0,

  "side": "white",
  "ply": 96,
  "fullmove": 55,

  "time_s": 0.006,
  "mate_ply": null,
  "game_id": "107",

The move fields are context, not the thing being learned. The NNUE learns the target score for the FEN. It does not learn to copy move_uci.

2. Teacher Labels

Teacher labeling asks a stronger engine, currently Stockfish, to evaluate each FEN at a fixed depth. The output is another JSONL file with the same row shape, but the training target score is replaced by the teacher's centipawn score. 

source_bucketed.jsonl row
  score        = previous target, for example Stockfish depth 12
  source_score = older score, if one existed

label_with_uci.py --depth 16
  asks Stockfish for this FEN
  writes new score from Stockfish depth 16
  stores the previous score in source_score

labeled.jsonl row
  score        = new training target
  source_score = previous target for audit
  teacher      = "stockfish"
  teacher_depth = 16

For the same real row after depth-16 relabeling:

{
  "fen": "8/p7/3n1p1p/P1k5/2p2KPP/8/8/1B6 w - - 9 55",
  "score": -288,
  "source_score": -259,
  "teacher": "stockfish",
  "teacher_depth": 16
}

Labels are sharded so many Stockfish processes can work in parallel. The depth-16 bucket run used 16 one-thread Stockfish workers with small per-worker hash. Each shard writes: 

shards/label.0.jsonl
shards/label.0.log
shards/label.0.jsonl.stats.json
...
shards/label.15.jsonl

Mate scores, missing scores, unknown results, and extreme centipawns are filtered or clamped depending on the run. This matters because a few bad targets can damage the net more than thousands of normal rows help it.

3. Packed Tensors

JSONL is readable but slow for training. Packing converts FEN strings into Enyo NNUE feature indices once, writes numeric arrays, and lets PyTorch train without reparsing chess text every epoch.

The current packed directory contains:

black_features.npyActive feature indices from Black's perspective.
counts.npyHow many feature slots are valid for each row. The current max is 32.
stm.npySide to move, used to order us and them.
score.npyTeacher centipawn target.
wdl.npyGame-result or WDL context when present.
phase_scale.npyMaterial-phase scaling value derived from the pieces.
source_id.npyNumeric source id so validation can be separated by origin.

"Packed tensors" means these arrays are the dataset representation PyTorch consumes. They are not the trained network. They are simply the preprocessed input rows plus target arrays.

4. PyTorch Training

train.py loads the packed arrays, builds the same NNUE architecture Enyo uses at runtime, initializes from an existing .nn file when requested, and optimizes the weights with PyTorch. 

packed arrays
  -> dataset.py loads rows
  -> model.py / enyo_nnue2.py build the NNUE model
  -> optional init-from-nn loads the starting runtime net
  -> forward pass predicts centipawns
  -> Huber/MSE/MPE loss compares prediction to score.npy
  -> AdamW optimizer updates weights
  -> validation rows choose the best checkpoint

In the depth-16 bucket run, the final 50k rows were reserved for validation and the rest were used for training: 

total rows: 988632
train rows: 938632
validation rows: 50000
optimizer: AdamW
common objective: Huber loss
example beta: 200 cp

A lower training loss means the net fits the teacher labels better. It does not automatically mean higher Elo. That is why static metrics, replay gates, and SPRT are separate stages.

5. .nn Export

Training writes a PyTorch checkpoint and an engine-loadable runtime file: 

model.pt  = PyTorch checkpoint, useful for resuming or inspecting training
model.nn  = Enyo runtime network, loaded by UCI option nnue2_file

The exported .nn follows the runtime layout loaded by Enyo's NNUE2 evaluator. This is the quantized runtime file. It has no JSON wrapper; it is raw binary arrays in the exact order the engine expects: 

input_weights  int16  [12288, 1024]
input_biases   int16  [1024]
l1_weights     int8   [16, 2048]
l1_biases      int32  [16]
l2_weights     float32 [32, 16]
l2_biases      float32 [32]
output_weights float32 [32]
output_bias    float32 [1]

The current runtime file size is about 25 MB. Enyo loads it with: 

setoption name nnue2_file value /path/to/model.nn

6. Replay Gates

Replay gates answer a different question than static metrics: if this network is inserted into Enyo search, does it make known bad positions worse? The gate replays real logged games and compares candidate behavior against the known baseline/reference analysis. 

known Enyo problem log
  -> replay reconstructs each go command
  -> candidate Enyo runs with candidate nnue2_file
  -> reference analysis marks best moves and centipawn losses
  -> gate compares candidate issues against baseline-known issues
  -> reject if candidate adds serious new blunders, timeouts, or crashes

Replay is cached by an analysis key that includes engine identity, effective UCI options, log content, and net file hash. Because of that, normal gates should not use --force; forcing replay wastes time and bypasses the cache safety we want.

7. SPRT

SPRT is the final arbiter. It runs candidate-vs-reference games with the same Enyo executable and different nnue2_file values. This isolates the network change from unrelated engine changes. 

candidate engine = Enyo executable + candidate model.nn
reference engine = same Enyo executable + current reference net
book             = UHO_Lichess_4852_v1.epd
time control     = usually 10+0.1 for net testing on pwa-5090
host defaults    = --concurrency 6 --threads 4 on pwa-5090

A candidate is promoted only if the game result is meaningfully positive. The d16 run showed why: float_head_huber_lr3e6_e8 improved static metrics and passed replay, but SPRT trended negative, so it was rejected.

Sample Shape

Score-bucket sampling is used so the net sees more than only quiet equal-ish positions. A random self-play sample is usually dominated by positions near equality, while search also needs useful evals in small edges, clear advantages, and tactical positions. 

source labeled rows
  -> keep unique FENs
  -> group by abs(score)
  -> sample a requested number from each bucket
  -> source_bucketed.jsonl
BucketReason
0-50 cpQuiet equal-ish positions where calibration near zero matters.
50-100 cpSmall edges where move choice can drift if the net is noisy.
100-300 cpNormal advantage positions that occur frequently in real games.
300-800 cpTactical or clearly better positions where compression can hurt conversion.
800-1600 cpLarge but non-mate scores, kept limited so they do not dominate training.
Bucket balance is not an Elo guarantee. It is a way to avoid wasting teacher time on a distribution that teaches the net almost nothing about decisive positions.

Architecture Being Trained

The active evaluator is nnue2_file. It loads a quantized .nn file and evaluates positions incrementally inside Enyo's alpha-beta search.

PartValueMeaning
King buckets16The king square is mapped to one of 16 broad regions.
Piece/color types126 piece types times 2 colors, represented relative to perspective.
Squares64Piece square after runtime mirroring/index conversion.
Input features16 * 12 * 64 = 12288Only features for pieces on the board are active.
Accumulator width1024 per perspectiveEach active feature adds a row of 1024 input weights.
Search inputus[1024] + them[1024] = 2048Side-to-move and opponent accumulator views are concatenated.
Head2048 -> 16 -> 32 -> 1Produces one centipawn score.
OutputcentipawnsSide-to-move perspective, consumed by search.

The runtime feature index is the packed board fact:

feature_index =
    king_bucket * 12 * 64
  + relative_piece_type * 64
  + mirrored_piece_square

A feature becomes active because the board actually contains that piece. Training does not decide which features are active; it decides the weights attached to those features. 

for each piece on the board:
    feature = FeatureIdx(piece_type, piece_color, square, king_square, perspective)
    accumulator[perspective][0..1023] += input_weights[feature][0..1023]

Why this architecture

ChoiceReason
Sparse piece-square features Only pieces that exist on the board do work. This makes evaluation fast and makes incremental updates possible after a move.
King buckets Piece values depend heavily on king location. Buckets add king context without needing a separate full input table for all 64 king squares.
Relative perspective The same pattern can be learned from either side's point of view instead of treating White and Black as unrelated problems.
1024-wide accumulators Wide enough to store many learned patterns, but still small enough to update inside search.
us and them inputs The head receives side-to-move features first and opponent features second, so the output is naturally side-to-move centipawns.
Small dense head 2048 -> 16 -> 32 -> 1 adds interaction capacity while staying cheap enough for millions of search evals.
Quantized runtime file Training uses floats, but the engine needs compact weights for speed and cache behavior.

How Training Is Performed

Training is supervised learning. Each row gives the trainer a position and a target score. The trainer asks the current neural net to predict a score, compares that prediction to the target, and adjusts weights to reduce the error.

  1. Read a FEN. The row describes one chess position.
  2. Build sparse features. The FEN is converted to active Enyo NNUE feature indices.
  3. Forward pass. The model sums feature weights, applies clipped activations, runs the head, and predicts centipawns.
  4. Compute loss. The trainer compares the predicted score with the teacher centipawn target, usually clamped to avoid extreme labels dominating.
  5. Backpropagate. PyTorch computes which weights caused the error.
  6. Optimizer step. Weights are nudged by the learning rate.
  7. Repeat by batch and epoch. A batch is many rows trained together; an epoch is one pass through the training set.
  8. Export. The trained float weights are quantized and written as model.nn.

A row after teacher labeling is conceptually:

{
  "fen": "rnbqkbnr/pppppppp/8/8/8/8/PPPPPPPP/RNBQKBNR w KQkq - 0 1",
  "score": 42,
  "wdl": 0.5,
  "source_score": 18,
  "teacher": "stockfish",
  "teacher_depth": 16
}

score is the target being learned. source_score is the previous score before relabeling and is kept so target changes can be audited.

One row, concretely

Suppose a row has a teacher target of +80 cp, but the current net predicts +20 cp. The prediction is too low by 60 cp. Backpropagation computes how to raise the output for this row. 

target score       = +80 cp
current prediction = +20 cp
error              = prediction - target = -60 cp
training direction = raise this position's predicted eval

Only the active feature rows for this position receive direct input-weight updates. If there is no knight on f5, the "knight on f5" feature row is not touched by this row. Across millions of rows, the same feature appears in many contexts, so its weights become a compromise that helps many positions instead of a memorized answer for one FEN.

The dense head is also updated because it decides how accumulator values become the final centipawn score. Training therefore adjusts both concrete piece-square knowledge and higher-level interactions.

Why Huber loss

Huber loss behaves like squared error for small mistakes and like absolute error for very large mistakes. That makes it less likely that a few noisy or extreme labels dominate the entire run. 

small error: optimize like MSE
large error: optimize closer to MAE
example beta: 200 cp

What training does not do

  • It does not imitate the move played in a PGN.
  • It does not prove a position is won or lost by itself.
  • It does not directly optimize Elo.
  • It does not replace search; it changes the evaluation used by search.

Metrics

MetricMeaningHow to use it
MAEMean absolute error in centipawns.Lower is better; good first filter.
MSEMean squared error.Penalizes large misses strongly; noisy with outliers.
RMSESquare root of MSE.Same units as centipawns.
signHow often prediction and target agree on which side is better.Useful sanity check, but not enough alone.

Static metrics can reject a bad network, but cannot prove a good one. A network can improve MAE and still lose Elo if search interacts badly with its calibration, move ordering, or tactical blind spots.

Why Better Targets Might Help

The neutral 20M/30M attempts suggest that simply training longer or mixing more sources is not enough. This run changes the target quality and data shape instead:

  • deeper Stockfish labels: depth 16 instead of depth 12;
  • balanced centipawn buckets instead of mostly quiet positions;
  • unique FENs to avoid repeatedly training on duplicates;
  • explicit validation by source so one distribution cannot hide damage in another;
  • strict replay gates before spending time on SPRT.

If a high-quality target run is neutral too, the next useful step is probably scaling the same target idea to more rows or depth 18, not another blind learning-rate tweak on the old mixed set.

Vocabulary

FEN
A text description of one chess position: pieces, side to move, castling rights, en-passant square, and counters.
JSONL
One JSON object per line. Enyo training rows are stored this way before packing.
Feature
A concrete board fact used as network input: perspective, king bucket, piece/color type, and piece square.
King bucket
A fixed category for king location. Enyo maps the king square to one of 16 regions so the same piece square can have different weights depending on king placement.
Accumulator
The summed hidden values before the network head. Each active feature adds a 1024-wide row of input weights into the accumulator.
Perspective
Enyo keeps accumulator values from both sides' point of view. At eval time, side-to-move values are treated as us and the other side as them.
Weight
A learned number. Training changes weights so predicted evals move closer to teacher evals.
Bias
A learned constant added to a layer's output.
ReLU / clipped activation
A non-linear clipping step. NNUE uses clipped accumulator values so the head can model interactions better than one flat linear formula.
Teacher
The source of target scores, usually a stronger engine such as Stockfish.
Label
The target value attached to a FEN. Here it means the Stockfish centipawn score written into score.
Shard
One slice of a labeling job. Sharding lets several teacher-engine processes label rows in parallel.
Packed dataset
Binary arrays generated from JSONL so PyTorch can train without reparsing FEN text during every epoch.
Tensor
A numeric array used by PyTorch. In this pipeline, packed NumPy arrays become tensors during training.
PyTorch
The Python machine-learning library used to run forward passes, compute loss, backpropagate errors, and update NNUE weights.
Batch
A group of rows trained together in one optimizer step.
Epoch
One pass through the training rows.
Loss
The training error PyTorch minimizes.
Huber loss
A loss that is squared-error-like near zero and absolute-error-like for large mistakes, reducing sensitivity to extreme labels.
Quantization
Converting training-time floating-point weights into the integer/compact runtime .nn format.
Replay gate
A validation step that runs the candidate through known games and checks for changed moves, regressions, blunders, and timeouts.
SPRT
The engine match test that decides whether a candidate is likely stronger in actual play.
